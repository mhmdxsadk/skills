# Naming before building

Purpose: help the user choose a name they like immediately before implementation, so they can use it for their project directory and repository.

Reuse an already chosen name; do not reopen naming automatically. Until this stage, a descriptive working label is sufficient and should not block planning or design exploration.

Use the now-defined product purpose, intended users, and any supplied tone or naming preferences to propose a small, varied shortlist with brief reasons. Ask about preferences only when needed to make useful candidates. Refine based on what the user likes or dislikes instead of generating an endless list or choosing for them.

Distinguish the display name from a practical directory/repository slug when useful. Explain any normalization, such as spaces becoming hyphens, without forcing the display name into slug syntax. Do not invent a name for the sake of completing the plan: an unanswered shortlist remains a proposal.

Check domains, package names, or repository availability only when relevant and requested or within the agreed research scope. Availability claims need current evidence and are time-sensitive. A search does not establish trademark clearance; never present an unchecked name as available or legally cleared. Naming does not require domain purchases, account creation, or repository creation.

Once the user chooses, record the name and any preferred slug in the build plan, update working labels in the planning artifacts, and present the next build milestone. If the user elects to defer naming, leave it explicit as their remaining pre-build decision while completing independent planning. End at the planning handoff unless implementation is separately requested.
