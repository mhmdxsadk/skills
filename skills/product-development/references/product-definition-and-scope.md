# Product definition and scope

Purpose: turn an understood problem into a selected product approach and first-release scope, preserving the authority for each choice. These instructions cover product definition, optional prototype planning, and MVP scoping. They do not authorize building a prototype or product.

## Start from existing work

Reuse the problem brief, supplied evidence, constraints, and decisions. If there is already a product concept or scope, work on its consequential gaps instead of restarting. Summarize the relevant understanding before proposing an approach or asking the next consequential questions. Do not keep collecting preferences once there is enough context to offer a useful proposal.

Use a descriptive project label during planning if there is no name yet. Choosing a name comes at the end of planning, before implementation.

## Compare product approaches

For an unsettled approach, compare plausible alternatives only where they could change the choice. A single viable approach needs a rationale, not padded alternatives. Explain how each would help the intended users, its fit with constraints, its main limitations, and consequential uncertainty. Compare only dimensions that could change the decision; avoid unsupported scores, cost estimates, or claims about demand.

Include a non-software option only when it is viable and easier than developing software. Do not pad the comparison with unsuitable alternatives. Preserve firm requirements; explore alternatives to preferences where useful. For an existing selected approach, apply the shared rule for reopening decisions.

Recommend the strongest fit with reasons. Record the selected approach and its decision authority; when it remains a proposal, identify the choice still needed. Apply the shared challenge rule to objections.

Summarize the resulting product concept: who it serves, what outcome it enables, and how the approach helps. Keep the product's possible future ambition distinct from the first release. A personal tool that may become SaaS does not automatically require the whole future SaaS scope now.

## Decide whether a prototype helps

A prototype comes before an MVP when it can resolve a useful question about the approach, interaction, or feasibility. Otherwise recommend proceeding directly to MVP planning. Do not substitute a prototype for a usable MVP without explaining the different purpose.

If a prototype would help, propose:

- The question it should answer and the decision its result would inform.
- The smallest useful representation or experiment, and what it deliberately leaves out.
- How the user could assess the result, including any agreed success signals.
- Which MVP decisions depend on that result.

The prototype plan is complete when its question, minimal representation, assessment, and dependent decisions are defined. Building or running it requires a separate implementation or evaluation task. For a feasibility check within the current request, apply the shared research stopping rule. A successful sample establishes only what was tested, not production reliability.

When scope depends on missing prototype results, keep affected choices provisional and continue independent work. If the user declines the check, apply the shared readiness rule: record a chosen fallback or the unresolved prerequisite rather than treating the assumption as established.

## Propose an MVP scope

Propose the smallest coherent release that lets the intended first users achieve the agreed outcome. For an existing product, adapt this to the next useful feature or release rather than forcing an MVP exercise.

Identify the core user task and the capabilities needed to complete it. Explain why each belongs in the first release. Include supporting behavior needed for usable, reliable completion; minimal scope should not leave the core task broken. Record relevant constraints and major failure conditions for the requirements stage to detail.

Separate included capabilities from deliberate exclusions and deferred ideas. Explain the important tradeoffs and what would count as a useful release, using agreed outcomes rather than invented targets. Deferring a feature is not a commitment to build it later.

Present a coherent scope proposal with reasons and invite changes to material choices outside delegated judgment. Select minor defaults within that delegation. Record the authority for the resulting choices and the dependencies of any remaining proposals.

## Handle suggested additions

Assess changes against the core outcome, intended first users, constraints, and dependencies. An addition may reveal a missing essential capability; do not reject it merely because it was absent from the initial proposal.

If a feature adds avoidable complexity, explain the specific tradeoff and suggest deferring or simplifying it. Apply the shared informed-choice rule, then update affected scope and planning assumptions. Describe a release with deliberate extras accurately rather than calling it the smallest possible scope.

## Capture the result and move on

Adapt the [product-and-scope brief](../templates/product-and-scope-brief.md). Extend existing planning material when that avoids duplication; a small project may need only a few paragraphs.

Scope is ready for requirements when the selected approach, intended first users and outcome, included/excluded capabilities, and release success signals are explicit, and each unresolved question names the work it affects. Each included capability must contribute to the core task or be a deliberate extra. Record the prototype decision when relevant. Proceed for defined capabilities; keep dependent requirements provisional where a material choice remains proposed or unresolved.
