# Design brief

Include enough context for a designer or design tool without the conversation history. Omit irrelevant sections.

## Product context

Describe the product's purpose, intended users, core outcome, release boundary, and target platform. Include relevant requirements or provide usable references to them.

## User workflows

For each key user goal, describe the starting context, actions and system responses across features, navigation, and the successful outcome. Reference supporting requirements.

## Feature workflows and states, where additional detail is needed

Detail features where branches or states need explanation. Include material loading, empty, partial, success, and error/recovery behavior as relevant. Clarify what users see, what they can do next, and whether progress or input is preserved.

## Screens or interaction surfaces

For each needed screen or view, specify its purpose, entry and exit points, content hierarchy, primary/supporting actions, related flows and state definitions, and relevant accessibility needs. Reference shared behavior rather than repeating it across screens. Describe other interaction surfaces instead when the product has no screens.

## Visual direction and references

Record supplied branding, references, and preferences; explain what aspects of a reference matter. Label suggested directions as proposals. Include useful wireframes, if any.

## Open design decisions

List questions that affect design and the behavior or requirements they depend on. Identify which changes would need a scope or requirements update. State what is ready for design exploration and what remains provisional.
